# ADS-B capture runtime

## Configuration

| Item | Value |
| --- | --- |
| Board | ZCU111 with XM500 |
| Default RF input | XM500 J2, `ADC225_T1_Ch0` |
| RF-ADC rate | 2.560 GSPS |
| RFDC decimation | 8 |
| RFDC words per AXI4-Stream beat | 2 |
| Programmable-logic decimation | Fixed divide-by-32 FIR Compiler paths for I and Q |
| Complex output rate | 10 MSPS |
| Centre frequency | 1090 MHz |
| Output format | Little-endian signed int16, interleaved I/Q |
| Output data rate | 40 MB/s |

Data path:

```text
XM500 J2
  -> ADC tile 1, block 0
  -> RFDC real-to-complex mixer, decimation by 8, 2 words per beat
  -> JACOBS_FIR_I and JACOBS_FIR_Q fixed decimation by 32
  -> capture gate and AXI DMA
  -> PYNQ DDR
  -> local .ci16 file or UDP transfer
```

The hardware source is maintained in `../../hardware/adsb_capture/`.

## Runtime directory

The complete `adsb_capture` directory is the runtime deployment unit. Copy the
primary notebook from its parent directory beside it.

| File | Function |
| --- | --- |
| `adsb_capture_lab.ipynb` | Board bring-up, DMA, static/live spectrum, energy, file, and UDP experiments |
| `../adsb_rfsoc_live.ipynb` | Primary live board-side Mode S detector/decoder and hardware-validation notebook for the current fixed-FIR design |
| `adsb_live_processing.ipynb` | Earlier live-processing draft retained for reference |
| `adsb_capture.py` | Overlay loading, RFDC setup, DMA capture, file output, and UDP transmission |
| `adsb_decoder.py` | Pure-NumPy preamble detector, PPM demodulator, CRC validator with marked rejected-candidate output, DF17/DF18 field decoder, and CPR tracker |
| `iq_protocol.py` | Shared sample-rate and UDP packet definitions |
| `receive_iq_udp.py` | Host-side UDP receiver |
| `bitstream/adsb_capture.bit` | FPGA configuration |
| `bitstream/adsb_capture.hwh` | PYNQ hardware metadata |

The `.bit` and `.hwh` files are generated by the same Vivado implementation
run and use the same base name.

At startup the runtime requires fixed-FIR hardware build ID `0xA834`, checks that the
HWH records a 160 MHz RFDC output/fabric clock, verifies the two fixed
`JACOBS_FIR_I/Q` FIR Compiler instances, and independently measures the RFDC
fabric clock against the 100 MHz PS clock. It also measures the final
stream rate using three complete timed DMA frames. The required result is about
160,000 fabric edges per millisecond and a measured average of 10 MSPS. The
most recent TVALID gap remains available as a diagnostic, but is not treated as
the sample period because the fixed FIR can schedule adjacent valid transfers
in a burst. Initialization stops before an FFT if the HWH describes the former
selectable decimator, the deployed clock is wrong, or the timed rate is wrong.

## Overlay load and finite capture

```python
from adsb_capture import AdsbCapture, IQ_SAMPLE_RATE_HZ, unpack_iq

radio = AdsbCapture()
buffer = radio.capture(262_144)

try:
    iq = unpack_iq(buffer, normalize=True)
finally:
    buffer.freebuffer()

print(iq.shape, iq.dtype, IQ_SAMPLE_RATE_HZ)
```

The default frame contains 262,144 complex samples, corresponding to
26.2144 ms at 10 MSPS.

## Live ADS-B processing on PYNQ

Open `../adsb_rfsoc_live.ipynb` from the board's Jupyter server. The
notebook keeps the detection path on the ZCU111:

```text
RFDC and PL decimation
  -> DMA frame in ZCU111 DDR
  -> Mode S preamble search on the A53
  -> 1 Mbit/s PPM demodulation
  -> CRC validation
     -> valid DF17/DF18: interpretation and aircraft tracking
     -> rejected candidate: raw message display with untrusted fields
```

The detector uses only NumPy and the local `adsb_decoder.py`; it does not
require `pyModeS`, a host-side decoder, or any transmitter-identification
model. An offline synthetic self-test in the notebook verifies known callsign,
altitude and even/odd CPR messages before the overlay is loaded.

The default live cell runs for 60 seconds. Set `LIVE_SECONDS = None` to run
until interrupted. Its recent-message display includes both `CRC OK` and
`CRC FAIL / UNTRUSTED` entries with the raw demodulated message and CRC
remainder. Rejected messages never update the aircraft tracker. Optional JSON
Lines logging writes only CRC-valid decoded messages to the board filesystem.

The current overlay uses simple S2MM DMA rather than cyclic or scatter/gather
DMA. The notebook's producer thread overlaps the next finite DMA capture with
A53 processing of the previous frame, but short inter-frame acquisition gaps
remain. The notebook reports:

- **processing headroom**: captured RF duration divided by detector CPU time;
- **capture duty**: captured RF duration divided by total loop wall time;
- preamble candidates, CRC rejections and accepted messages.

A processing-headroom value above one shows that the detector takes less CPU
time than the signal duration in each batch. A capture duty below 100 percent
records the remaining dead time between finite captures. Continuous
reception requires double buffering/scatter-gather DMA or moving the preamble
front end into programmable logic.

## Local capture format

```python
radio.save(
    "/home/xilinx/captures/adsb_test.ci16",
    samples=1_000_000,
)
```

The data file contains:

```text
I0, Q0, I1, Q1, I2, Q2, ...
```

Each component is a little-endian signed 16-bit integer. One million complex
samples occupies 4 MB and represents 0.1 seconds. The adjacent
`.ci16.json` file records the sample rate, centre frequency, decimation, sample
count, and board timestamp.

## UDP transfer

Host receiver, executed from the repository root:

```bash
python3 pynq/adsb_capture/receive_iq_udp.py \
  captures/adsb_udp.ci16 \
  --bind 0.0.0.0 \
  --port 50000 \
  --frames 100
```

Board transmitter:

```python
radio.stream_udp(
    "192.168.2.1",
    port=50000,
    frame_samples=262_144,
    frames=100,
)
```

The packet format consists of a 24-byte sequence header and up to 1024 bytes
of I/Q payload. Missing packet positions are zero-filled by the receiver and
counted in `dropped_udp_packets` in the JSON metadata.

Simple DMA introduces a gap while the next frame is armed. The current UDP
path therefore records ordered finite frames rather than a gap-free stream.

## Bring-up record

The initial hardware check uses no RF input and a 4096-sample DMA transfer.
The expected RFDC status is 2.560 GSPS with successful DMA completion and no
capture overflow.

A subsequent signal check uses a low-level 1090 MHz tone at XM500 J2. A
65,536-sample or longer capture produces an FFT peak near zero frequency
offset. Moving the source to 1090.5 MHz moves the peak by approximately
0.5 MHz; the observed sign records the I/Q spectral orientation.

FFT calculation:

```python
import matplotlib.pyplot as plt
import numpy as np

from adsb_capture import IQ_SAMPLE_RATE_HZ, unpack_iq

buffer = radio.capture(262_144)
try:
    iq = unpack_iq(buffer, normalize=True)
finally:
    buffer.freebuffer()

iq = iq - iq.mean()
window = np.hanning(len(iq))
spectrum = np.fft.fftshift(np.fft.fft(iq * window))
frequency = np.fft.fftshift(
    np.fft.fftfreq(len(iq), d=1 / IQ_SAMPLE_RATE_HZ)
)

plt.plot(frequency / 1e6, 20 * np.log10(np.abs(spectrum) + 1e-12))
plt.xlabel("Offset from 1090 MHz (MHz)")
plt.ylabel("Magnitude (dB)")
plt.grid(True)
```

## Fault observations

| Observation | Relevant checks |
| --- | --- |
| RFDC rate differs from 2.560 GSPS | 409.6 MHz reference-clock programming, RFDC PLL configuration, and bitstream/HWH pairing |
| DMA wait does not complete | Capture-gate `TLAST`, DMA start order, interrupt metadata, and stream/reset connections |
| Overflow status is set | FIFO depth, DMA `tready`, and the 200 MHz HP0 memory path |
| I/Q is swapped or spectrum is reversed | Combiner order: I in bits `[15:0]`, Q in bits `[31:16]`; RFDC `m10_axis` real and `m11_axis` imaginary |
| Build ID is `0xA833` | A fixed-FIR HWH has been paired with the older selectable-decimator bitstream, or implementation was not regenerated; rebuild in `build_rfdc8_fir32_clk160_v2` and deploy its matched `.bit`/`.hwh` pair |
| Most recent TVALID gap is 1 | This can be an adjacent transfer within the fixed-FIR output schedule; use `verified_output_sample_rate_hz`, which times complete DMA frames, to validate the average rate |
| A 0.5 MHz offset is displayed as about 4 MHz | Hardware build ID must be `0xA834`; HWH and measured fabric clock must both be 160 MHz; timed DMA rate must be approximately 10 MSPS |
